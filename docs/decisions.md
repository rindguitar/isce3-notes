# 設計判断の記録

コードを書く前後に下した判断を、理由ごと残す。**新しいものを上に追記する。**

記入形式:

```markdown
## YYYY-MM-DD: （決定のタイトル）
- 決定: （何を選んだか）
- 理由: （なぜか。1〜2行）
- 却下した代替案: （あれば）
```

---

## 2026-09-06: テンプレート更新に伴う再編（最小変更 + main 直接コミットの維持）

- 決定: 新しいプロジェクトテンプレートに合わせて構成を変えた。ただし**最小変更**に留める。
  - `STATUS.md` → `docs/STATUS.md`、`decisions.md` → `docs/decisions.md`
  - `mermaid-guide.md` → `.claude/rules/mermaid.md`（`paths` frontmatter を付与）
  - `.claude/rules/readme.md` と `.claude/rules/wiki.md` を新規作成
  - `drafts/README.md` を新規作成（README 必須ディレクトリに合わせた）
  - `reference/` `logs/` `drafts/` は**ルートに残す**
- 理由: このリポジトリは**全体が文書**なので、`logs/` や `drafts/` まで `docs/` 配下へ
  入れると階層が 1 段増えるだけで区別が生まれない。テンプレートが `docs/` を指定して
  いるのは「コードと文書を分ける」ためであり、コードが無いここでは効果が薄い
- 決定: **`main` への直接コミットはこのリポジトリでは維持する**（テンプレートの
  「`main` 直接コミット禁止」は適用しない）
- 理由: 記録用でレビュー相手がいない。ブランチ→PR→マージを挟むと、ログを 1 行足すたびに
  手間が増えて記録が滞る。**`~/isce3` 側の `develop` 直接コミット禁止は従来どおり厳守**する
- 却下した代替案:
  - `docs/` に全部集約 — 最も整理されるが、パス書き換えの量に見合う利点が無い
  - テンプレート通りブランチ運用 — 上記のとおり記録の速度を落とす
- 副作用: `logs/` 内の過去ログには旧パス（`STATUS.md` 等）の記述が残る。
  **ログは追記のみで修正しない**規約なので、これは直さない

## 2026-08-31: 貢献は「起票」と「解決」の 2 本立てにする（2026-08-27 の改訂）

- 決定: **issue 起票で終わらせず、自分で直せるものは PR まで出す。**
  自分が立てた issue も、既存の issue も対象にする
- 理由: 起票だけでは「見つける側」に留まり、上流の詰まり（レビュー能力の不足）を
  解消する側に回れない。**マージまで数か月かかる前提**で出せば、滞留は動機の問題にならない
- **2026-08-27 の「貢献の主軸は issue 起票」を改訂したもの。** 滞留の実態把握は当時のまま
  正しいが、「だから PR を出さない」という帰結を取り消す
- 却下した代替案: PR を出さず起票に専念する — 専門分野の学習が進まない。
  `referenceTerrainHeight` のように**修正案まで検証できた案件が実際に出てきた**

## 2026-08-30: バグは 1 例では起票しない

  **NISAR データ無しで確認してもらえる**形になった

## 2026-08-27: 貢献の主軸は issue 起票に置き、PR はマージ待ちの前提で出す

> ⚠️ **2026-08-31 に改訂した**（下記「貢献は『起票』と『解決』の 2 本立てにする」）。
> 滞留の実態把握はそのまま有効だが、「PR を主軸に据えない」という帰結は取り消した。

- 決定: upstream への貢献は「**issue を立てる / 既存 issue に再現データを足す**」を主軸とし、
  PR は出すが**マージまで数か月かかる前提**で扱う
- 理由: 実態を数えた結果、**PR は作者が誰かに関係なく滞留している**。
  open PR 65 件、最古は 2024-11 の #27（約 21 か月）。コア開発者 gshiroma だけで 17 件が open。
  外部の方が出した #270 は 3 か月レビューされていない（review_comments = 0）。
  ボトルネックは「外部かどうか」ではなく**レビュー能力**
- 却下した代替案:
  - PR を主軸に据える — マージされないことを自分の失敗と誤認しやすい。動機が保たない
  - 貢献自体を諦める — issue とコメントには反応があるので、そこは機能している
- 補足: ユーザーは ISCE3 の専門分野が未学習。**issue 起票なら専門知識の不足を
  「環境の違いによる再現」で補える**（手元は GDAL 3.13.3 / HDF5 2.2.0 / GCC 15.3 と
  upstream が試していない組み合わせ）

## 2026-08-27: 試行コードはファイルに残さず標準入力から実行する

- 決定: 探索・学習目的のコードは `.py` ファイルにせず、
  `python - <<'PY' ... PY` のヒアドキュメントで実行する
- 理由: 使い捨てのコードでリポジトリを汚さないため。
  加えて**段階ごとに分けて流せる**ので、出力を都度解釈しながら進められる
- 却下した代替案:
  - `scratch/` ディレクトリを作って置く — `.gitignore` の管理が要るうえ、
    残しても後で読み返さない
- 補足: ファイルとして残すのは、再利用が前提のツールになったときだけ。
  **成果として残したい内容は `logs/` や wiki の用語集に散文で書く**

## 2026-08-27: 最初の題材として幾何（rdr2geo / geo2rdr）を選んだ

- 決定: ISCE3 の理解は `core` / `geometry` を外から叩くところから始める。
  テストを読む案・ワークフローを通す案は見送った
- 理由: **`~/isce3` のソース読み取り許可が不要**で、データ準備もいらず即座に動かせる。
  かつ rdr2geo / geo2rdr は上位処理すべてが乗る土台なので、
  ここが分かると他の領域の見通しが立つ
- 却下した代替案:
  - `tests/python/` を実例として読む — 実際の入力データの形が見えるが、読み取り許可が要る
  - 同梱データでワークフローを 1 本通す — 一番「動かした」感があるが、
    データ量と実行時間が読めず、`tests/data/` と `share/` の許可も要る
- 補足: 副産物として、未解決の `GeoToRdr` に対して
  **「正常系は通る」ことが分かった**。追うなら失敗する入力条件の絞り込みになる

## 2026-08-23: CUDA ビルドは行わない

- 決定: 常に `-DWITH_CUDA=OFF` を明示する
- 理由: システムの nvcc は CUDA 12.0 で対応ホスト GCC が 12.x まで、環境の GCC は 15.3 で範囲外。
  かつ `environment.yml` に CUDA が含まれておらず、プロジェクトが想定する構成ではない
- 却下した代替案:
  - conda-forge の `cuda-nvcc` を入れて揃える — 可能だが、まず CPU 版で通すことを優先した。
    **GPU が必要になった時点で再検討する**
- 補足: `WITH_CUDA` の既定は `Auto` で、**nvcc を見つけると勝手に ON になる**。
  明示的に OFF を指定しないと意図せず CUDA ビルドに入る

## 2026-08-23: ビルドは CMake 直叩きにする（`pip install .` から移行）

- 決定: `cmake -S ~/isce3 -B ~/isce3-build -G Ninja -DISCE3_FETCH_DEPS=OFF -DWITH_CUDA=OFF`
- 理由: **`pip install .` では `ctest` が使えない**（ビルドツリーが残らない）。
  CONTRIBUTING.md は PR 前のローカルテストを要求している。加えて差分ビルドが効かず、
  1 行変えるたびにフルビルド相当になり開発サイクルが成立しない
- 却下した代替案:
  - `pip install .` のまま — 公式推奨だが「使うだけ」向け。リポジトリを汚さない利点はある
  - `pip install -e .`（editable）— C++ の変更には結局再ビルドが必要で、解決にならない
- 補足: 直叩きでは `ISCE3_FETCH_DEPS` の既定が **`ON`** になり、Eigen 等をネットから
  取り直して conda のものを無視する。**`OFF` の明示が必須**
