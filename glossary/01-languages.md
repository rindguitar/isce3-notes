# 01. 言語まわり — C++ / Python / CUDA

## なぜ ISCE3 は 2 つの言語で書かれているのか

ISCE3 は **C++ で計算し、Python から操作する**構造になっている。

| | 役割 | 理由 |
|---|---|---|
| **C++** | 実際の数値計算（画像処理、幾何計算、信号処理） | 速い。SAR データは巨大なので、速度が実用性を左右する |
| **Python** | 処理の組み立て、設定の読み込み、ワークフロー | 書きやすい。試行錯誤が速い |
| **CUDA** | C++ の一部を GPU で動かす版 | さらに速い。ただし NVIDIA GPU が要る |

「Python から `import isce3` して使う」と言っても、**中身の重い処理は C++ で動いている**。
Python は指示を出しているだけ。

## C++ の基礎

### コンパイル型言語である

Python は書いたテキストをその場で解釈して実行する（インタプリタ型）。
C++ は違い、**実行する前に機械語へ翻訳する工程が必要**。これがコンパイル。

```
ソースコード (.cpp) → [コンパイル] → 機械語 (.o) → [リンク] → 実行可能ファイル / ライブラリ
```

今回 `cmake --build` に 15〜40 分かかったのは、この翻訳作業をしていたため。
Python なら不要な工程で、C++ を使う代償にあたる。

### ヘッダファイルとソースファイル

| 拡張子 | 呼び方 | 中身 |
|---|---|---|
| `.h` / `.hpp` | ヘッダ | **宣言**。「こういう関数がある」という目録 |
| `.cpp` | ソース | **定義**。関数の中身の実装 |
| `.cu` | CUDA ソース | GPU 用のコード |

今回読んだ `cxx/isce3/geometry/geometry.h` はヘッダで、
`slantRangeFromLookVec` という関数が「こういう引数を取る」とだけ書いてあった。

```cpp
double slantRangeFromLookVec(const isce3::core::Vec3& pos,
        const isce3::core::Vec3& lkvec,
        const isce3::core::Ellipsoid& ellips = {});
```

`double` が戻り値の型、`const ...&` が引数。`= {}` は既定値。

### ヘッダオンリーライブラリ

**ヘッダファイルだけで構成され、リンクが不要なライブラリ。**
使う側が `#include` するだけで済む。

今回関係したもの:

- **Eigen** — 線形代数（ベクトル・行列計算）
- **pybind11** — Python バインディング作成用

「ヘッダオンリーだから**ビルド時にしか要らない**」という性質が重要だった。
pybind11 を 2.x に下げたとき**再ビルドが必要**だったのはこのため。
実行時に差し替えることはできない。

### 名前空間 (namespace)

名前の衝突を防ぐ仕切り。`::` で区切る。

```cpp
isce3::core::Vec3
```

これは「`isce3` の中の `core` の中の `Vec3`」という意味。
Python の `isce3.core.Vec3` と同じ発想。

### テンプレート

**型を後から決められる仕組み。** 同じコードを `int` 用にも `double` 用にも使い回せる。

```cpp
template<int N, typename T>
class Vector : public Eigen::Matrix<T, N, 1> {
```

これは「`N` 個の `T` 型を持つベクトル」という設計図で、
`Vector<3, double>` と書くと「double 3 個のベクトル」が作られる。

`: public Eigen::Matrix<...>` の部分は**継承**で、
「Eigen の行列型を土台にして、その上に作る」という意味。
今回 `pntintersect` が失敗した原因は、まさにこの「継承している」という点にあった。
pybind11 3.x が「Eigen そのもの」は認識できても「Eigen を継承したもの」を
認識できていなかった。

### C++17

C++ の言語仕様のバージョン。2017 年版。ISCE3 はこれ以降を要求する。
コンパイラが古いと使えない機能があるため、`CMakeLists.txt` が起動時に確認している。

### 未定義動作 (UB / Undefined Behavior)

**C++ の規格が「こう書いたらどうなるか決めない」としている操作。**
未初期化の変数を読む、配列の範囲外にアクセスする、などが該当する。

厄介なのは、**エラーにならず「たまたま動いてしまう」**こと。
そして最適化の強さによって挙動が変わる。

今回 `GeoToRdr` が

- `-O0`（最適化なし）で通り
- `-O2`（最適化あり）で落ちる

という挙動を示したのは、UB の典型的な兆候だった。
「最適化を強めたら壊れた」は「最適化のバグ」よりも
「もともと UB があって、たまたま動いていただけ」であることが多い。

### 最適化レベル

| フラグ | 意味 |
|---|---|
| `-O0` | 最適化しない。書いたとおりに動く。デバッグ向き。遅い |
| `-O2` | 標準的な最適化。実用ビルドはこれ |
| `-O3` | さらに強い最適化 |

CMake の `CMAKE_BUILD_TYPE` がこれを切り替える。
`Debug` = `-O0`、`Release` / `RelWithDebInfo` = `-O2` 相当。

### FMA（積和融合 / Fused Multiply-Add）

`a * b + c` を **1 命令で、途中の丸めを 1 回だけにして**計算する CPU 機能。
速く、かつ精度も高い。ただし「掛けてから丸めて、足してまた丸める」場合と
**結果の最下位桁が変わりうる**。

今回 `-ffp-contract=off` でこれを止めて検証した。
結果が変わらなかったので、FMA は原因ではないと分かった。

### ABI (Application Binary Interface)

**コンパイル済みのもの同士が噛み合うための約束事。**
関数の呼び方、構造体のメモリ配置など。

コンパイラのバージョンを変えると ABI が変わることがあり、
そうなると既存のライブラリと繋がらなくなる。
「GCC を下げたらフル再ビルドが必要」なのはこのため。

## Python 側

### バインディング (binding)

**C++ の関数を Python から呼べるようにする接着剤。**

C++ と Python はデータの持ち方が全く違う。
Python の `numpy` 配列と C++ の `Eigen::Matrix` は別物なので、
呼び出しのたびに変換が要る。この変換を書いたものがバインディング。

ISCE3 は **pybind11** を使っている。書き方はこうなる:

```cpp
m.def("slantrange_from_lookvec", &geom::slantRangeFromLookVec,
        py::arg("pos"), py::arg("lkvec"), ...);
```

「`slantrange_from_lookvec` という名前で、C++ の
`slantRangeFromLookVec` を Python に公開する」という意味。

### 型変換器 (type caster)

pybind11 が「Python のこの型 ↔ C++ のこの型」を変換する部品。
numpy 配列 ↔ Eigen ベクトルの変換器は `#include <pybind11/eigen.h>` で入る。

今回のエラー

```
1. (pos: isce3::core::Vector<3, double>, ...)
```

で `pos` が **C++ の生の型名のまま表示された**のは、
「この型の変換器が見つからない」というサイン。
変換器が効いていれば `numpy.ndarray[numpy.float64[3,1]]` のように
Python 側の型名で表示される。

**エラーメッセージの型名の書き方で、変換器が効いているか判別できる。**

### `isce3.ext.isce3`

`isce3.__init__.py` からたどれる `isce3.ext.isce3` は、
**C++ で書かれた拡張モジュール本体**（`.so` ファイル）。
純粋な Python コードではない。

## CUDA

NVIDIA GPU 用の C++ 拡張。`nvcc` というコンパイラで翻訳する。

| 用語 | 意味 |
|---|---|
| **nvcc** | CUDA のコンパイラ |
| **ホストコンパイラ** | nvcc が内部で使う通常の C++ コンパイラ。`CUDAHOSTCXX` で指定 |
| **Compute Capability (CC)** | GPU の世代を表す番号。手元の GTX 1060 は **6.1** |
| **VRAM** | GPU 側のメモリ。手元は 6 GB |

nvcc は**ホストコンパイラのバージョンに厳しい**。
CUDA 12.0 が対応する GCC は 12.x までで、手元の環境（GCC 13 / 15）は範囲外。
今回 CUDA ビルドを見送った理由がこれ。

ISCE3 の `WITH_CUDA` は既定が `Auto` で、
**nvcc が見つかると勝手に CUDA ビルドに切り替わる**。
今回は `-DWITH_CUDA=OFF` で明示的に止めた。
