## 手元で再現できたもの: #255

**`isce3.core.DateTime` が "Z" 付きの ISO-8601 文字列を解釈できない。**
コメント 0 件、関連 PR なし。**完全に未着手。**

再現したところ、**issue の記述より範囲が広い**ことが分かった。

| 入力 | ISCE3 | Python 標準 `fromisoformat` |
|---|---|---|
| `2026-01-01T00:00:00.000000` | OK | OK |
| `2026-01-01 00:00:00`（空白区切り） | OK | OK |
| `2026-01-01T00:00:00.123456789`（小数 9 桁） | OK | OK |
| `...T00:00:00.000000Z` | **FAIL** | OK |
| `...T00:00:00Z` | **FAIL** | OK |
| `...T00:00:00z`（小文字） | **FAIL** | FAIL |
| `...T00:00:00+00:00` | **FAIL** | OK |
| `...T00:00:00-07:00` | **FAIL** | OK |

issue は「`Z` が読めない」と書いているが、実際は**タイムゾーン指定子を一切受け付けない。**

一方 `isce3.core.DateTime` は pybind の docstring に
*Timezone info is discarded and the object is interpreted as UTC time* とあり、
**中身は常に UTC**。`Z` は UTC を意味するので意味論的には素直に受理できるはず。
設計判断が要るのは**非ゼロのオフセット**（適用するか、明確なエラーで拒否するか）だけ。

エラーメッセージから、修正箇所は `cxx/isce3/core/DateTime.cpp` の
`strptime()` 413 行目付近。内部で `sscanf` を使っているとのこと（issue の記述）。

## 環境そのものが武器になる

「バグを発見して issue を立てる」方針に対して、
**いまの環境は upstream が試していない依存の組み合わせ**になっている。

| 依存 | 手元 | 意味 |
|---|---|---|
| GDAL | **3.13.3** | #199 で問題になった 3.12 より新しい |
| HDF5 / h5py | **2.2.0 / 3.16.0** | #223 報告時（2.0.0 / 3.15.1）より新しい |
| GCC | **15.3.0** | 非常に新しい。未解決の `GeoToRdr` 失敗もこれ起因の可能性 |
| numpy | 1.26.4 | **古い。NEP 50 系のバグが見えない** |

最後の行が狙い目。#335 の報告者自身が
「**他のビットシフト箇所も NEP 50 の観点で監査すべき。numpy ≥ 2.0 の CI ジョブも要る**」
と書き残している。**numpy 2.x の環境を別に作って ctest を回せば**、
同種の未報告バグが出る可能性がある。しかも「黙って壊れる」種類なので誰も気付いていない。

これは専門知識が不要で、環境構築で既に踏んだ「依存バージョンのずれの切り分け」そのもの。
