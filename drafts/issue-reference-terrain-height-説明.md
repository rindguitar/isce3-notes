# メンター説明用メモ — referenceTerrainHeight のバグ

作成: 2026-08-31。issue 本文は `drafts/issue-reference-terrain-height.md`。

---

## 0. 一言でいうと

**ISCE3 が作る製品の中の「参照地形高」という補助データが、まるごと空（NaN）になっている。**
処理は正常終了扱いなので、誰も気づかないまま公式の配布物にも入っている。

原因は、そのデータが「1 次元か 2 次元か」を判定する処理が、**必ず間違った答えを出す
書き方になっていた**こと。データ固有の事情ではなく、コードの構造上の問題。

---

## 1. 前提（用語 3 つだけ）

| 用語 | やさしく言うと |
|---|---|
| **RSLC** | 衛星のレーダが撮ったままの画像。まだ地図に貼れていない |
| **GCOV / GSLC** | それを地図の座標に貼り直した製品。ISCE3 の出力 |
| **LUT**（ルックアップテーブル） | 補正に使う数表。「この時刻ではこの値」という対応表 |

`referenceTerrainHeight`（参照地形高）は LUT の一つ。
**「衛星から見て、この時刻にはだいたいこの標高の地面を見ている」という基準値**で、
画像を地図に貼るときの計算の出発点になる。

この数表には 2 つの形があり得る:

* **1 次元** — 時刻だけで決まる（今の実装はこちら）
* **2 次元** — 時刻と距離の両方で決まる（将来こうする予定、とコードに書いてある）

---

## 2. 何が起きているか

RSLC から GCOV を作ると、GCOV 側の `referenceTerrainHeight` が**全画素 NaN**になる。

* 処理の**終了コードは 0**（成功扱い）
* エラーらしきものは、GDAL のメッセージが 1 行出るだけ
* **公式の配布プロダクトでも同じ**（実物 2 本を開いて確認: 有効値 0 / 156,420 と 0 / 111,531）

科学データ本体（後方散乱の値）は無事。**壊れているのはこの補助レイヤだけ。**

---

## 3. なぜ起きるか（たとえ話）

コードは「この数表は 1 次元か 2 次元か」を判断する必要がある。
そこで採用されていた判定が、

> **同じ棚（HDF5 のグループ）に「距離の目盛り」が置いてあれば、2 次元だろう**

というもの。

ところが**その棚には他の数表も同居していて、距離の目盛りはそちらのもの**だった。
つまり目盛りは常に棚にある。だから判定は**常に「2 次元」**と答える。

しかも RSLC を書き出すプログラム自身が、参照地形高を書いた直後に
その目盛りを**無条件で**同じ棚へ置いている。
→ **ISCE3 が作った RSLC では、この判定が正解を出すことは原理的にあり得ない。**

その結果、1 次元の数表（長さ 31）を 2 次元の画像（105 × 31）として読もうとして失敗し、
読めなかった場所が NaN のまま出力される。

実際のエラーがそれをそのまま言っている:

```
Requested (0,0) of size 105x31 on raster of 31x1
（105×31 をくれと言われたが、実物は 31×1 しかない）
```

---

## 4. なぜ今まで気づかれなかったか

1. **失敗しても処理が止まらない。** 終了コードは 0
2. **テストが 1 つも無い。** `tests/` 全体で `referenceTerrainHeight` の出現回数はゼロ
3. 同じ変更で入った**もう一方の似た処理にはテストがあり、そちらは正しく動いている**

> テストがある方は動き、テストが無い方は壊れていた。

### 「意図的にそのままにしているのでは？」への答え

**「意図」と「優先度」は分けて考える必要がある。否定できたのは前者だけ。**

| 問い | 答え |
|---|---|
| A. 1 次元を扱わなくてよい、という**意図**か | ❌ **違う**（下記 4 点） |
| B. 壊れているが**優先度が低い**という判断か | ⚠️ **あり得る。否定できない** |

**A を否定できる根拠:**

1. 1 次元用の処理が**実装されている**。値を距離方向へ引き伸ばす分岐（`np.repeat`）と、
   専用の警告文まである。「今はやらなくていい」と考えているなら書かない
2. その分岐の対象は `LUT_1D_AZ_DATASETS = ['referenceTerrainHeight']` の**1 つだけ**。
   つまり**書かれた機能が、唯一の対象に対して一度も動かない**
3. 導入 PR の**主目的が「1 次元 LUT をジオコードできるようにする」**だった
   （2 次元対応はそこへの追加分。順序が逆なら「将来のための先行実装」と読めた）
4. 意図的な先送りなら普通は**静かに飛ばす**。実際 `skip_if_not_present` という
   「無ければ警告して飛ばす」仕組みが既にある。それを使わず GDAL のエラーを出して
   NaN を書き込むのは、設計された振る舞いに見えない

**B は残る。** #165 で値がどうせ全部ゼロだと分かっており、RSLC 側には
`# TODO ref height` もある。「値が入るようになってから直せばいい」という判断はあり得る。
議論は JPL 内部リポジトリ（`#2137`）にあり公開されていないので、**確かめる手段がない。**

**それでも起票する価値はある。**
公開の場に記録が一切無いため、次に同じ場所で躓く人が同じ調査を繰り返すことになる。
メンテナ側のコストは「既知です、優先度は低い」と一言返すだけで、
**それが返ってくればこちらは確実に一つ学べる**（次に何をやるかの判断材料にもなる）。
そのため issue 本文の末尾に「既知なら閉じてくれて構わない」という一文を入れてある。

## 6. 既存の issue #165 との違い（ここを聞かれたら答える）

upstream に似た名前の issue #165 があるが、**別物**。

| | #165 | 今回 |
|---|---|---|
| 場所 | `sourceData/` 以下 | `processingInformation/` 以下 |
| 症状 | 値が全部 **0** | 値が全部 **NaN** |
| 原因 | RSLC を書くとき中身を入れていない（TODO 扱い） | **次元判定の誤りでジオコーディングが失敗** |

**#165 が直ってもこちらは直らない。**
仮に正しい標高が入っても、貼り直す処理で落ちるので NaN のままだから。
issue 本文の冒頭でこの区別を明示している（重複として閉じられないため）。
